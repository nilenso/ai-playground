Measuring the Measurement

We are trying to answer one question: what makes a command-line interface agent-friendly? Two days in, we cannot yet answer it — because the test we built to measure it gives full marks to an agent that never touches the tool.

The short version

Our exam gives full marks to four completely different outcomes, including "ignored the tool" and "didn't answer the question".

On top of that, the score can only move by 4 points out of 100 — and it randomly wobbles by 12 between identical runs. So even where the marking is right, a perfect change and a lucky roll of the dice look the same.

We found all of this before spending money on optimisation runs. Total spend so far: $1.06, and not one optimiser run funded.

The question we are answering

What makes a command-line interface agent-friendly?

That is the whole point. botmap is the subject we experiment on, not the thing we are shipping. Everything else — the optimiser, the three parallel arms, the exam — is instrumentation for answering it.

Which means a run that moves no score can still succeed. If it tells us which CLI properties let an agent recover on its own, that is the result we came for.

The tool. botmap answers questions about maps — "how many hospitals are in Rhode Island?" Its users are AI assistants, not people. An assistant gets the question and a terminal, and has to work out the right command on its own. Nobody tells it which command to use. Figuring that out is the entire test.

The exam. We ask an AI 30 map questions and score how well it coped. Did it finish? Did it give up and download the whole dataset? Did it hit errors?

The loop. An optimiser rewrites the tool, we re-run the exam, and keep the version that scores better. Repeat. The optimiser reads the actual transcripts — every command the AI typed and every error it hit — not just the final score.

Two ways to improve things

You can change the tool (make commands easier to find) or change the instructions the AI reads (tell it the right command up front). We call these two levers. Most of this experiment is about which lever is worth pulling.

The result

Every part of the score is either already maxed out, or too noisy to read.

The pattern is odd and worth naming: the exam is quiet where it's already maxed out, and noisy where it still has room. The parts that could move are the parts we can't measure reliably.

Why the exam stopped working

Four completely different outcomes all score a perfect 1.00.

We read the actual transcripts of eight questions that scored full marks. They were not doing the same thing at all:

QuestionWhat the agent actually didCostScore
asian‑restaurants Drove the CLI well. Correct answer, clearly explained. 14 cmds · $0.391.00
bus‑stops‑cambridge Hit a defect and recovered — guessed bus_stop, hunted, tested another city to isolate the variable, found bus_station. Honest, careful answer. 8 cmds · $0.441.00
hotel‑density Never used the tool at all. No botmap command was run. Answered from two web searches and official statistics. 0 cmds · $0.231.00
clipping‑polygon Never answered the question. Ran one command, drifted into scheduling itself a wake-up, and finished with “I’ll just wait for the background task notification instead.” 1 cmd · $0.301.00

Those four are not degrees of the same thing. One is the tool working. One is the tool failing and the agent rescuing it expensively. One is the tool being bypassed. One is no answer at all.

The actual defect

Scoring asks “did the agent produce text?” Nothing checks whether the tool was used, or whether the text answers the question. A confident non-answer passes. So does a web search.

What we can and cannot claim

An earlier draft of this page said the exam awards full marks on questions where we have proof the tool fails, and used bus-stops-cambridge as the example. That was wrong. Reading the transcript, the agent recovered and gave a good answer; the 1.00 is deserved.

The true finding is different, and worse. The exam is not mismarking failures — it cannot see what happened at all. It gives the same mark whether the CLI was driven, worked around, or ignored.

The cost is where the signal actually was

bus-stops-cambridge is still instructive, just not as a marking failure. The tool knew bus_station existed and never said so. The agent found it anyway — after 8 commands, 10 turns and $0.44 on one question.

That is the shape of nearly everything we found: the CLI is not broken, it is expensive. It withholds what it knows, and the agent pays to rediscover it.

And the ceiling on top of that

Where the marking is right, there is almost nothing left to win: 21 of 30 questions already score full marks, so a perfect change is worth about 4 points out of 100 — against a random wobble of 12 between identical runs. Two questions swing by 0.8 out of 1.0 running the unchanged tool twice, minutes apart.

The measurement leaked

The agent under test could see 30 of the operator’s personal tools.

Two things we found by probing the harness itself:

The environment was not isolated. Run as the harness runs it, the agent under test sees more than thirty skills installed on the machine it happens to be running on — nothing to do with the tool being measured. Nobody else could reproduce our numbers, and neither could we after changing our own setup. One flag fixes it.

The tool restriction did not restrict. The harness passes --allowedTools Bash. A recorded attempt invoked Skill, Bash, ToolSearch and WebSearch — which is how one question got answered without the tool at all.

We are deliberately not blocking those tools: a real agent has them, and removing them would make the test less like reality, not more. But it has to be recorded — and arguably an agent routing around your CLI is itself a measurement of how agent-friendly it is.

What we tried

Three approaches, running side by side, so we could compare them fairly.

Arm Ano optimiser

Let an agent run the loop itself

Instead of an optimiser library, we wrote instructions telling an AI agent how to do the same job: propose a few competing ideas, test them cheaply, throw out the losers. This tests whether you need the code at all, or whether good instructions are enough.

Result: three working fixes. Whether it matches the optimiser — still unanswered.

Arm Binstructions

Only improve what the AI is told

Change nothing about the tool. Just rewrite the instructions the AI reads before it starts.

Result: the one clean baseline we have, the safety checks that made it possible, and the single most useful insight on this page (below).

Arm Cmore context

Show the optimiser the whole codebase

Previously the optimiser could only see the files it was allowed to edit. It kept asking about a file it couldn't see — 35 times in one run. So we let it read everything while still only editing a few files.

Result: the noise analysis above, and one prediction registered in advance.

What went wrong along the way

We destroyed two measurements before getting one clean run.

Day 1 · 4h in

The map data updated underneath us

Our reference measurement was taken on last month's map data; the new runs used this month's. Scores crashed from 0.76 to 0.19. It looked exactly like a terrible change. It was a broken comparison.

Day 1 · 9h in

The AI was reading the wrong instruction file

A global file on the machine was overriding the one we were editing. Every change to the instructions would have been written somewhere the AI never looked — and the result would have read as "improving the instructions doesn't help."

Day 1 · 13h in

We ran out of API quota mid-exam

Questions 1–5 passed, 6–30 all failed. A clean cliff, not scatter. To the scoring code, running out of quota looks identical to a change that broke the tool.

Day 2 · 03:00

A clean baseline, third attempt

All 30 questions, correct data, nothing failed. The safety checks we built after the first two disasters are why it finished.

What we found

Fourteen problems. Nine of them are in our measuring equipment, not the tool.

Every one of them was invisible in the direction that mattered. The stale measurement looked like a valid comparison. The silent zero looked like a clean result. The empty commit looked like a success.The recurring shape

F11 is the one to remember

If a command finds nothing, the tool used to say nothing — and the AI would confidently report "there are none." One of our fixes makes it say "did you mean bus_station?" instead.

But the scorer counts that helpful message as an error. So the fix scores worse precisely because it made the tool better.

Generalised: any optimiser that scores on error count will learn to delete error messages. Left alone, our loop would have stripped out the very warnings it exists to add.

The good news

The AI wastes most of its effort exploring, not recovering from errors. That's fixable.

We measured what the AI actually does per question: about six commands and ten turns — and only 6% of commands fail.

So the cost isn't error recovery. It's exploration: working out which command to use, checking it worked, checking the output looks right. An AI that already knew the right command could plausibly do it in two or three.

Halving time and tokens isn't an ambitious target here. It's roughly "don't explore."

And this is where the exam still works. Those 21 maxed-out questions can't score better on correctness — but they can all get faster and cheaper. So speed and cost have room on all 30 questions, not just nine.

This points straight at improving the instructions rather than the tool: the tool can make commands easier to find; the instructions can make finding unnecessary.

What needs to happen next

Fix the instrument, then run controlled before/after experiments — one per candidate property.

The deliverable is not a patched CLI. It is a list of design properties, each backed by a measurement: what an agent-friendly CLI does, the trace of an agent defeated without it, the change we made, and the trace showing the agent doing better. A property with no “after” is a hypothesis, not an answer.

0

Isolate the environment

One flag, so the agent under test stops seeing thirty of the operator’s personal tools. Until this lands, no measurement is reproducible on anyone else’s machine.

blockingone line
1

Classify failures properly, instead of counting errors

Today one label answers “did stderr look bad?” and we pretend it answered “did this go well?” Three separate facts replace it: what happened (worked / empty / refused / wasteful), whose fault (tool / agent / environment), and could the agent recover (was it told how, or left guessing).

This is what separates a helpful refusal from a silent wrong answer — today they score the same, and one of them is the worst thing a CLI can do.

blocking the restno API cost
2

Build the differential probe

We cannot ask “is this zero correct?” But we can ask “does this zero survive a change that should not matter?” Re-run the same query with one thing swapped — a different field, a different type, a bigger limit. If the answer appears, the original was wrong and the tool knew.

Cheap CLI calls, no model spend. It turns an unanswerable question into an answerable one, and it is how we find candidate properties without waiting for expensive runs.

no API cost
3

Prove the detector fires, then re-read the runs we already have

We are building a detector for failures that are invisible by definition, so we feed it known bad cases first and confirm it catches them. A silent-wrong case scoring clean is a build failure.

Then run it over the 60 attempts already on disk. No model calls, and it gives the first real picture of what is actually going wrong.

free
4

One measurement run — no optimiser

Its output is a breakdown of failure types, not a score. It also tests a prediction: many of the 21 perfect questions may be perfect only because these failures are invisible. If they start failing once we can see them, the exam was never the problem — the marking was, and we need no new questions at all.

after step 3
5

Paired before/after experiments — this is where the answer gets made

One per candidate property: change it, re-run the same questions under the same conditions, compare the traces. Did the agent recover unaided? How many commands did it take before, and after?

Each records which lever the fix used — the tool, or the instructions — because “what makes a CLI agent-friendly” has a legitimate answer of the form “nothing in the CLI; tell the agent up front.” If the confirmed properties cluster on one side, that is itself the finding.

The three fixes above are the first three experiments, already built.

the deliverable

A refuted property is a real result. If we add a hint and the agent ignores it anyway, then “name the fix” was not the missing property, and something else is. That is worth knowing, and far cheaper than shipping a fix nobody benefits from.
