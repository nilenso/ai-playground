# Container refresh and verification

The workflow builds/tests on PRs and publishes **only from main**, after final-image checks. It does not deploy. The publish job alone has `packages: write`; it publishes the scanned image archive rather than rebuilding it. Weekly uncached builds refresh Alpine packages and CAs even when application source has not changed, but scheduled runs never publish. Manual runs publish only when `publish_image` is explicitly selected on main; the default is check-only. High/critical scanner findings block publication; the JSON report also retains lower-severity findings. Review the report: a clean scan is not evidence of exploitability testing or complete Bun/native-binary coverage.

## Reviewed pins (2026-11-11)

- Bun `1.4.4-alpine`, multi-platform index `sha256:4cf82f5686b196504fe119db3fcd9185b191f82ece82c40680e597228ec6070a`. The final stage upgrades all installed Alpine packages and regenerates system CAs. Bun's **embedded** roots are independent: upgrading `ca-certificates` alone does not repair them. `scripts/check-container-trust.ts` checks both actual stores for emSign ECC Root CA - G3, during the build and again in the final image. Its public-certificate regression fixture comes from Bun 1.3.13.
- Hono `4.13.18`; protobufjs `7.6.6`; undici `7.30.2` in `bun.lock`.
- OTel SDK/exporter `0.220.0` coordinates core/Jaeger `2.9.0`. `0.217.0` fixes some advisories but still pins vulnerable core/Jaeger and protobufjs. API `1.9.0` satisfies the SDK's `<1.10` peer constraint. The dummy-collector regression exercises the existing Phoenix enrichment and protobuf export without external services. This deliberately avoids OTel 3.x.
- `basic-ftp` override `6.2.6`: current get-uri `8.0.1` still requires `^5.3.1`, so upgrading the parent alone cannot fix CVE-2026-102990. The v6 breaking change disallows separate transfer hosts by default (FTP bounce hardening); no insecure opt-in is enabled. The get-uri `6.0.5` Client/access/lastMod/list/downloadTo/close contract is exercised by real loopback FTP retrieval tests, including LIST fallback and rejection of a different PASV host. Remove the override only when upstream supports a patched version naturally.
- litem8 remains `0.2.0` to preserve migrations. Static binary SHA-256 values are pinned from the GitHub release's SHA256SUMS/asset digests: x86_64 `89d6352f951b50afda07602a319160049a1aaec6a7afbc9da21287b21c2a69c0`, aarch64 `5320ed2175dfe39b8e3eb7686a966a897ad93746295423f198d345592d88f959`. Verify before executing; do not replace this with an unchecked executable download.

Both dependency stages copy the JSR `.npmrc` configuration before `bun install --frozen-lockfile`. Only the production install is copied into the final image; Biome, Bun types and React DOM types are build-only. React types remain because `react-markdown` requires them as a peer; TypeScript is also an existing peer dependency. The obsolete binary `bun.lockb` is removed so the reviewed text lock is authoritative. `@nilenso/megasthenes` remains `0.1.0` and pi-ai `0.62.0`; sandbox/gVisor configuration, application auth/session code, migrations and entrypoint behavior are unchanged.

## Refresh through a PR

1. Check Bun's stable release/security notes and resolve the Alpine image's new version **and** multi-platform digest with `docker buildx imagetools inspect oven/bun:<version>-alpine`. Update the Dockerfile pin together. The scheduled freshness check fails when the stable version advances; it never silently changes the pin. A major/behavioral release needs compatibility review, not automatic adoption.
2. Update dependencies using that Bun version and real public/authenticated JSR access. Never fabricate lock entries or bypass registry integrity. Review transitive changes and retain compatible library lines. Keep the formatter pinned unless deliberately changing lint policy.
3. Run `bun install --frozen-lockfile`, `bun test`, `bun run check`, `bun run build`, and `bun run build:visualizer`. Do not use real `.env` files or credentials for these checks.
4. Build the final image with `docker build --pull --no-cache -t <unique-local-tag> .`. Run `docker run --rm --entrypoint bun <tag> run scripts/check-container-trust.ts`, inspect actual OS/runtime package versions, and scan the **final** image using the workflow's digest-pinned Trivy version with an up-to-date DB. Retain scan date/DB metadata and explain uncovered binaries or findings rather than equating scanner silence with remediation.
5. Run the workflow's disposable `--network none` smoke container with dummy OAuth/JWT settings; copy `scripts/check-container-smoke.ts` into it, then `docker exec -e CONTAINER_SMOKE_TEST=1 <name> bun run scripts/check-container-smoke.ts`. It seeds only that throwaway DB and checks migrations, dual UI, OAuth state rejection, JWT/waitlist/session routes and WebSocket ping. Re-run litem8 to check migration idempotence, then remove **only that container**. Real OAuth token exchange, LLM providers, existing production databases and gVisor end-to-end communication require separate staging verification.

Builds intentionally consume current Alpine package repositories: the base and JS graph are pinned, but the entire image is not bit-for-bit reproducible across repository updates or build timestamps. Record the resulting image digest; never substitute a local tag for a published immutable production digest.
